# CP-011 — hôte C++ autonome et vérification locale avec licence

L’hôte du moteur traduit fonctionne désormais sans Python pour les chargements et rendus natifs. Le wrapper Audio Unit, son interface et l’installation restent à terminer. Aucun nouveau composant n’est installé par ce checkpoint.

## Résultats obtenus

- `LegacyEngine.cpp` exécute les initialisateurs, le constructeur et le moteur statiquement traduit, avec des services C++ explicites pour la mémoire, les chaînes, fichiers, conversions PCM, mutex, horloge et préférences. Les pointeurs hôtes 64 bits ne sont jamais tronqués en pointeurs invités.
- Le FXP et le `vstdata` AU fournis sont chargés et les programmes resérialisés. Les zones objet, tas et globales, les appels hôtes et les programmes produits sont identiques aux références i386 de CP-010, sous Linux natif et ARM64/Linux/QEMU.
- Le rendu de trois secondes sans enregistrement correspond aussi à la référence, mais son niveau reste inférieur à −100 dBFS : le test sonore conserve un résultat négatif. Aucun rendu complet audible de Lightgarden n’est encore validé.
- Les 704 cas DSP et 11635 cas d’instructions/gardes passent avec les objets du moteur complet. Les primitives et sources générées n’ont pas changé depuis CP-010.
- Le C++ de l’hôte compile aussi avec `-Wall -Wextra -Werror` sous GCC 14. Les objets Mach-O ARM64 du moteur restent ceux vérifiés à CP-010 ; le nouvel hôte et sa branche CoreFoundation ne sont pas encore compilés/exécutés sous macOS.

Les données invitées sont intégrées à `LegacyImageData.cpp` depuis l’original épinglé. Ces octets contiennent constantes, tables et adresses ; ils ne sont pas exécutés. Le moteur exécute les fonctions C++ statiques de `src/lifter/whole/`, sans décodeur x86. Le générateur vérifie le SHA-256 original.

## Paramètres Audio Unit

Les méthodes AU originales ont été exécutées dans une fixture d’objet externe explicitement limitée, avec le synthétiseur initialisé. La liste publique contient **522 paramètres** d’identifiants discontinus entre 0 et 555. Le moteur VST en déclare 602 : présenter simplement 602 contrôles normalisés ne reproduirait pas le contrat AU.

Les noms, unités, plages, valeurs par défaut et valeurs après ouverture correspondent entre les méthodes originales et traduites. La validation de 0 à 602 fournit aussi **56 alias anciens**, par exemple 28 → 484, 29 → 485. Les détails sont dans `analysis/au-parameter-contract.json`. Cette extraction n’enregistre pas d’AU auprès du système, n’établit pas la disposition des bus et ne prouve pas le rappel d’un projet Logic/Live.

## Licence privée et rendu sur Mac

L’utilisateur confirme posséder sa licence. Il ne faut pas demander sa clé dans le chat ou sur GitHub.

`Verifier-Moteur-Mac.command` compile en ARM64, vérifie les exécutables, rejoue les références DSP/instructions et compare les deux sauvegardes de programmes. Il propose ensuite une saisie masquée dans le Terminal. La clé est transmise par l’entrée standard au champ `Serial Number` de SysGlo via son setter original, avant l’activation. La vérification d’enregistrement originale reste intégrale ; aucun octet de résultat n’est forcé. La saisie n’est pas passée dans les arguments du processus et n’est pas enregistrée dans un fichier de clé.

Entrée seule demande la lecture des préférences locales existantes de `com.linplug.Sophistry`. L’hôte C++ utilise CoreFoundation, utilisateur courant / tout hôte, comme l’original. Le chemin par saisie directe utilise un magasin de préférences vide, afin qu’un ancien réglage ne remplace pas la clé saisie. Le setter est appelé avant l’activation de l’écriture des préférences ; un garde arrête le test si cette condition de cycle de vie change. Les captures mémoire et sauvegardes de programme sont désactivées dans les modes privés.

Une entrée volontairement invalide a été refusée sous Linux sans produire de captures mémoire ni exposer l’entrée dans les rapports. Cela vérifie le refus et les protections de diagnostic, pas l’acceptation de la licence réelle, qui reste à tester localement sur Mac.

Si le rendu C++ produit un signal supérieur au seuil, le script prépare une référence locale Python/Unicorn dans `work/reference-python/`, avec les versions de `requirements-analysis.txt`, puis exécute les instructions i386 originales avec la même saisie privée. Pour les préférences existantes, leur export par `defaults` est capturé en mémoire, sans fichier de préférences exporté. Les deux WAV sont comparés strictement. Les paquets de référence sont téléchargés depuis PyPI ; le moteur C++ et le futur AU de production ne nécessitent pas cet émulateur. Le lanceur Mac et ce chemin privé de comparaison n’ont pas encore été exécutés sur le Mac utilisateur.

La comparaison isole les instructions du moteur avec des services hôtes modernes. Elle n’exécute pas les bibliothèques Apple i386 d’origine et ne garantit pas, à elle seule, le rappel de projets ou l’intégration AU.

Les rapports et WAV sont regroupés dans `Sophistry-rapports-CP011-<date>.zip`. La collecte exclut les fichiers de préférences, clés et captures mémoire. Le script ne transmet rien automatiquement. En cas de différence, le contrôle strict reste en échec.

## Compilation et reprise

```sh
bash scripts/build-native-engine.sh
```

Ce script utilise Xcode sur Mac et impose `-arch arm64`. Les objets dont la source, les en-têtes et la configuration de compilation sont identiques sont réutilisés. Aucun paquet de développement tiers n’est nécessaire pour compiler l’hôte C++ ; Python/Unicorn est réservé à la référence originale.

Sous Linux, exemple sans licence privée :

```sh
work/native-engine/NativeEngineProbe \
  --state 'reference/Presets/lightgarden 02 BT.FXP' \
  --asset-directory reference/Samples --asset-directory reference/Presets \
  --output-prefix work/fxp
```

Le moteur reste un prototype d’intégration. Le système de fichiers se limite aux assets configurés, la conversion aux formats PCM16 stéréo observés, les codecs de chaînes à un sous-ensemble et les services GUI/timers aux scénarios de test. Le modèle des mutex suppose un CPU invité sérialisé ; le cycle de vie complet et les contraintes de rendu en temps réel restent à terminer. Il faut aussi vérifier les variantes de vtables du moteur dans l’ancien AU et ses bus avant d’en déduire un wrapper moderne fidèle.

Les preuves sont dans `evidence/cp011-*`, `evidence/au-contract-*-cp011.json` et `analysis/au-parameter-contract.json`. Les résultats du Mac reçu précédemment restent ceux de CP-008. Le nouveau test licencié, la construction de l’AU, `auval`, l’interface et les copies des projets Logic/Live restent à effectuer.
