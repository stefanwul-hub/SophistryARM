# CP-010 — ouverture, restauration et diagnostic de rendu

Le prototype ouvre désormais le moteur et charge les deux fichiers fournis en exécutant les instructions originales traduites. L’Audio Unit installable, son interface native et le rappel des anciens projets restent à réaliser. Le test audio complet reste en échec.

## Code récupéré et compilation

Le listing initial ne contenait pas toutes les destinations des tables de sauts. `RecoverDecompilerCode.java` examine les cibles du p-code décompilé et les blocs de base, puis désassemble les adresses manquantes sans modifier les octets machine ni effacer les conflits. Les 2845 fonctions internes ont été examinées sans échec de décompilation. Trois conflits de chevauchement restent consignés ; deux autres instructions ont été découvertes par la trace réelle du chargement FXP.

Le résultat sauvegardé contient 191378 instructions, soit 5377 de plus que CP-009, et 758579 opérations p-code. Le découpage conserve les frontières des anciennes unités pour limiter les recompilations. Le générateur accepte `--reuse-layout src/lifter/whole/manifest.json` pour reproduire ce découpage.

Les 366 objets, runtime inclus, compilent sous Linux x86_64, ARM64/Linux et Mach-O ARM64. Avec ces objets, les 704 cas DSP et 11635 cas primitifs/gardes passent à nouveau sous Linux natif et sous QEMU ARM64/Linux. Cette version n’a pas encore été exécutée sur le Mac de l’utilisateur. Les rapports macOS reçus concernent CP-008.

## Ouverture et états réels

`tests/probe_engine_initialization.py` reste un hôte de diagnostic Python, distinct du futur hôte C++ du plugin. Les deux exécutions utilisent les mêmes services hôtes explicitement limités : original i386 sous Unicorn et bibliothèque C++ statiquement traduite. Pour le contexte AU, elles utilisent le callback original `0x273c`, qui retourne zéro.

Les 121 initialisateurs, le constructeur Kaja, `effOpen`, `setChunk` et `getChunk` sont exercés. Le FXP transmet son programme de 20640 octets avec le drapeau programme ; le `.aupreset` transmet son `vstdata` de 22192 octets avec le drapeau banque, comme l’ancien wrapper AU. Les empreintes des zones objet, tas et globales, les appels hôtes et les programmes resérialisés sont comparés. Le nom interne `empty` ne correspond pas au nom du dictionnaire AU ; les noms vides observés dans les données d’entrée sont conservés, sans les remplacer arbitrairement.

Le sample `BT_cronox18.wav` est réellement ouvert. L’adaptateur AudioConverter ne prend en charge ici que la conversion exacte PCM16 stéréo vers float32 non entrelacé, sans rééchantillonnage. Le callback d’entrée est exécuté par le code original/traduit ; les données converties correspondent à une lecture RIFF indépendante. Le chargement et les préparations DSP suivantes sont exécutés par le moteur. Cela ne constitue pas une exécution d’AudioConverter Apple ni une preuve sonore globale.

## Test audio conservé en échec

Le moteur reçoit 44100 Hz, des blocs de 512 frames, une note MIDI 60 de vélocité 100 et son extinction après deux secondes. Le rendu dure trois secondes et observe les six sorties VST exposées. La disposition des bus Audio Unit originaux n’est pas encore établie.

Les deux rendus sont identiques, mais leur pic maximal est seulement `1.6860019513842417e-7`, environ −135,5 dBFS, avec une composante presque constante autour de `1e-7`. Le critère sonore exige un pic supérieur à `1e-5` (−100 dBFS), et le programme retourne donc une erreur. Cette comparaison ne valide pas le son de Lightgarden.

Le traitement des notes dans le code original dépend notamment du résultat de la vérification d’enregistrement, stocké à l’offset objet `0xcfc8`. Cet octet reste à zéro dans le scénario sans préférences Mac. Les vérifications originales sont conservées. Le test n’insère aucune clé, ne change aucun résultat de vérification et ne force aucune voix. Les préférences et la licence privées devront être prises en charge localement sur le Mac dans l’intégration native.

Le système de fichiers du test expose seulement les fichiers de référence en lecture. Les recherches de dossiers Mac suivent le cas introuvable ; les préférences sont absentes. Les timers Carbon sont enregistrés sans boucle GUI. L’allocateur est borné, sans réutilisation ; les mutex modélisent un seul CPU. Horloge et flux aléatoires sont figés, les fonctions mathématiques viennent de Linux. Aucun de ces adaptateurs n’est encore un service de production.

## Reproduire les tests

Compilation C++ avec Xcode sur Mac ou un compilateur C++ sous Linux :

```sh
bash scripts/build-lifter-chunks.sh
work/lifter-whole/LiftedProbe reference/Sophistry.i386 evidence/static-lift-comparison.fixtures
work/lifter-whole/InstructionProbe reference/Sophistry.i386 evidence/primitive-instructions.fixtures
```

Sur Linux, le diagnostic différentiel nécessite les dépendances `requirements-analysis.txt` :

```sh
python3 tests/probe_engine_initialization.py --construct --open \
  --preset 'reference/Presets/Lightgarden 02 BT.aupreset' --inspect --au-callback \
  --library work/lifter-whole/liblift-whole.so --output work/au-state.json
```

Omettre `--library` exécute les octets i386 originaux. Ajouter `--render 3` exerce le scénario audio, actuellement en échec sous le seuil décrit. Sur Mac, la bibliothèque compilée porte le suffixe `.dylib`. Le prototype et ses dépendances d’analyse ne sont pas requis par un futur AU de production.
