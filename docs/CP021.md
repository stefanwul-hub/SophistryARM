# CP-021 — chargement des samples D4U/D4T et conversion PCM

CP-020 est bien installé sur le Mac utilisateur : auval, éditeur local, vue système distante et huit WAV de référence ont passé les vérifications. Le diagnostic d’un projet silencieux donne une cause distincte : licence reconnue, MIDI reçu et `072_Sample2_cronox3.D4U` ouvert, puis `Unsupported PCM converter format`. L’état reste non chargé et la sortie est quasi nulle. Voir [le rapport Mac vérifié](../evidence/mac-cp020-installed-editor.json) et [le diagnostic filtré](../evidence/mac-cp020-d4u-loading-error.json).

## Correction

Le chargeur original à `0xb2a2a` lit les fichiers D4U/D4T comme des données float32 little-endian, un canal après l’autre, via `0xaedb0`. Il demande une conversion mono avec les flags source `13`, destination `9`, puis appelle `AudioConverterConvertBuffer`. L’adaptation précédente était limitée au PCM16 stéréo et à `AudioConverterFillComplexBuffer` : elle refusait cette voie avant de charger le son.

CP-021 ajoute la conversion mono et généralise le décodeur aux PCM entiers 8/16/24/32 bits et flottants 32/64 bits, mono/stéréo, dans les deux ordres d’octets et dispositions entrelacées/séparées. La destination reste float32, avec **mêmes canaux et même fréquence** ; aucun mixage ni rééchantillonnage n’est ajouté. Les float32 sont copiés par bits, notamment pour D4U/D4T.

Les structures et pointeurs du programme 32 bits restent explicitement adaptés : aucun pointeur de fichier ou de buffer natif n’est transmis au code invité. Le callback original `0xaef2c` indique un canal même pour son buffer stéréo entrelacé ; le format ASBD et la taille de frame déterminent le décodage. Ce comportement est couvert par les tests de régression.

Le diagnostic comporte maintenant les formats source/destination, le nom du sample et le nombre de frames converties, sans données PCM, clé ni chemin absolu. Les instructions DSP statiquement traduites restent inchangées : la correction porte sur les appels de conversion de la plateforme.

## Nom du son

Le champ de nom de 28 octets du fichier FXP est conservé comme métadonnée standard de preset AU. Un ancien état dont le nom manque n’est pas renommé arbitrairement : l’interface distingue **« État chargé — nom non enregistré »**, **« Chargement interrompu »** et **« Aucun son chargé »**, au lieu d’afficher seulement `empty`. Le chunk DSP n’est pas réécrit pour cette présentation.

## Vérifications effectuées

Voir [les preuves de développement](../evidence/cp021-development-checks.json) et [la comparaison du chargeur](../evidence/sample-formats-cp021.json).

- 256 cas PCM avec réponses IEEE connues, 516 refus de formats/buffers invalides, réussis sous Linux natif et ARM64/Linux/QEMU.
- AddressSanitizer et UndefinedBehaviorSanitizer sans erreur sur le décodeur.
- Douze fichiers synthétiques dérivés du sample public fourni : WAV mono16/24, stéréo24/32, float32 mono/stéréo, AIFF mono16/stéréo24 et D4U/D4T mono/stéréo. L’original i386 et l’hôte C++ produisent des chunks, objets, heaps et globaux **identiques dans les 48 régions comparées**. Ces tests sont sans licence ; ils valident le chargement, pas un rendu musical autorisé.
- Les huit régions de référence CP-011 sont inchangées ; les huit cycles du pont AU et les 30 tests Python passent.
- Huit binaires Mac sont compilés et liés strictement en ARM64, avec les exports AU/Cocoa vérifiés. Il s’agit de compilation depuis Linux, pas d’exécution macOS.

## Vérifications préparées pour votre Mac

Le script compare 32 cas correspondant aux dispositions demandées par le chargeur avec le véritable `AudioConverter` Apple actuel. L’original passe des fréquences nulles égales ; l’oracle moderne reçoit 44,1 kHz dans les deux formats, sans rééchantillonnage. Si l’oracle refuse le flag entier signé ajouté à un format flottant, il est retiré pour cette comparaison sémantiquement équivalente. Le convertisseur Apple i386 historique n’est pas exécuté.

Deux rendus musicaux D4U, mono et stéréo, sont ensuite comparés aux instructions i386 originales avec la licence locale. Les contrôles déjà présents restent obligatoires : rendus du composant en 2/6 canaux, auval, éditeur local, hôte distant, inspection finale et restauration sur échec. Le nom FXP est aussi vérifié dans le test d’éditeur.

## Installation et retour

Télécharger le lanceur CP-021 indiqué dans le README, fermer Logic et Live, puis :

```sh
bash "$HOME/Downloads/Demarrer-Sophistry-CP021.command"
```

La licence et la banque valides sont réutilisées. Le script télécharge et vérifie l’archive, compile en ARM64, teste puis sauvegarde/remplace `/Library/Audio/Plug-Ins/Components/Sophistry.component`. L’identité `aumu/Sop3/LinP` et le bundle `com.linplug.au.Sophistry` sont conservés.

Après **« Installation CP021 confirmée »**, rouvrir une copie du projet silencieux et vérifier le même son. Transmettre le ZIP `Sophistry-rapports-CP021-<date>.zip`. Si un son reste silencieux, jouer quelques notes puis copier son diagnostic avant de charger un autre preset. Les nouvelles entrées `audio_conversions` permettront de voir le format précis rencontré.

**CP-021 n’a pas encore été exécuté sur le Mac utilisateur.** Le sample D4U réel mentionné dans le diagnostic n’a pas été transmis ; les tests utilisent des données synthétiques reconnues par le chargeur original. Le fonctionnement du projet concerné, la totalité des banques, la charge polyphonique et l’interface complète restent à vérifier.
