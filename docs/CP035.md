# CP035 — décisions temporelles et service périodique d’origine

CP035 continue la recherche de concordance. **Le moteur, l’interface, les tests d’installation et les scripts restent identiques à CP032.** Aucun correctif de production ni optimisation n’est ajouté. Ce checkpoint contient des sondes d’analyse, leurs résultats et les points à corriger ou à clarifier ensuite. Il ne nécessite pas d’installer un nouveau composant.

## Comparaisons supplémentaires

Les instructions du binaire i386 3.0.8 sont exécutées sous Unicorn et comparées au C++ CP032 compilé sous Linux x86_64, avec les mêmes données synthétiques et les mêmes réponses système contrôlées.

| Routines et décisions | Cas |
| --- | ---: |
| Capacités annoncées par l’AU original | 8 |
| Choix d’une voix à réutiliser | 512 |
| Changements d’état et compteurs des voix | 48 |
| Décodage MIDI NRPN et expiration du délai | 216 |
| Accélération d’une commande en fonction du temps | 72 |
| Rappel du service périodique générique | 16 |
| Rappel AU, condition d’activation et réarmement | 64 |
| Traitement original des notifications, sélections et appels indirects | 48 |
| **Total** | **984** |

**Aucune différence trouvée dans ces cas**, sur 7224440 octets d’état comparés, les retours vérifiés et les notifications enregistrées. Les destinations de présentation sont contrôlées ; le gestionnaire original `0x18360` est bien exécuté dans ses 48 cas. Les messages déclenchant une boîte d’alerte et le traitement complet de l’ancienne interface ne sont pas couverts ici. [Résultats](../evidence/cp035-timing-behaviour.json).

## Conséquences démontrées de l’horloge simulée

Deux scénarios distincts utilisent le même code original, puis sa traduction, avec deux contrats d’horloge. Ils isolent un écart de données système, sans changer les routines de décision.

1. Trois notes occupent des emplacements de voix à 100, 200 puis 300 ms ; l’emplacement zéro est celui réutilisé le plus récemment. Avec le temps écoulé, la routine choisit l’emplacement un, le plus ancien. Avec les petits ticks synthétiques de CP032, les dates sont égales à zéro après conversion en millisecondes et elle choisit l’emplacement zéro.
2. Une donnée MIDI arrive cinq secondes après les deux sélecteurs NRPN. Avec le temps écoulé, le délai est expiré et elle n’est plus reconnue comme donnée de ce NRPN. Avec les ticks synthétiques, elle est encore acceptée et associée au numéro NRPN 259.

Dans chaque scénario, l’i386 et le C++ donnent le même résultat pour un contrat d’horloge donné. La différence apparaît lorsqu’on change les informations fournies par l’adaptateur. **L’horloge simulée a donc des conséquences fonctionnelles possibles démontrées**, au-delà d’une simple différence dans le diagnostic. Ces cas contrôlés ne reproduisent pas la session Live de l’utilisateur et ne prouvent pas une cause de surcharge CPU.

## Le service périodique AU

L’activation originale enregistre un rappel `0x3aba`, avec un premier délai de **5 ms**, puis un intervalle de **250 ms**. Quand son drapeau de demande est actif, la chaîne originale est `0x3aba → 0x1a004 → 0x1a54a`. Elle traite notamment une file de notifications et réarme le rappel. Les 64 cas correspondants vérifient le drapeau actif/inactif, une référence de timer nulle/non nulle et différentes quantités de notifications.

Une seconde sonde compile le code actuel de `LegacyEngine` sans le modifier. Elle initialise et active une instance, change deux paramètres publics, attend 300 ms et appelle les getters utilisés par l’interface. Un observateur propre à cet exécutable lit les arguments d’imports et la couverture d’instructions, sans changer l’état du moteur.

Le rappel est bien enregistré, mais son entrée et celle du service de Synth restent inexécutées dans cette séquence. Le code commun de l’adaptateur conserve les timers dans une table, sans planifier leurs appels. Les lectures de l’interface ne les remplacent pas automatiquement. **Le drapeau original demandant ce service reste lui aussi à zéro.** Cela interdit de conclure que la seule activation d’un timer suffirait à rétablir un comportement complet.

Aucune notification en attente n’est observée dans cette sonde. Elle n’utilise ni licence, ni préférences privées, ni notes, ni banque, ni vrai hôte AudioComponent macOS. Elle ne démontre pas une fuite de mémoire, un défaut audio ou un effet CPU dans Live/Logic. Le raccordement entre la nouvelle interface et les services périodiques originaux est un point d’intégration à examiner, distinct d’une routine DSP absente. [Observation filtrée](../evidence/cp035-host-idle-observation.json).

## Reproduire l’analyse

Les sondes sont dans [analysis/cp035](../analysis/cp035), hors des sources fonctionnelles restaurées. Le script Python utilise les dépendances du comparateur i386 existant et une bibliothèque construite à partir du C++ CP032 :

```bash
python analysis/cp035/compare_timing_behaviour.py /chemin/libcp032-audit.so --output resultat.json
```

`HostIdleObservation.cpp` se lie à `LegacyEngine.cpp`, `LegacyImageData.cpp` et cette bibliothèque. Sous Linux, compiler avec `-DSOPHISTRY_AUDIT_WRAP_SL_RUN` et lier avec `-Wl,--wrap=sl_run` pour observer les imports et la couverture. Cette instrumentation reste propre à la sonde ; elle n’est pas ajoutée au composant. Les flags numériques de référence restent `-ffp-contract=off -fno-fast-math`.

## Conclusion et suite

Les comparaisons renforcent la concordance de routines originales supplémentaires. Elles confirment surtout que la présence du code ne garantit pas des entrées système fidèles ni l’exécution de tous les services prévus autour de lui.

La suite doit examiner une horloge réelle cohérente avec les timestamps AU, puis le contrat de demande et d’exécution des notifications périodiques. Toute correction doit conserver les décisions originales et être validée séparément du retour strict à CP032. Aucune optimisation n’est introduite pour masquer ces écarts. La cause quantitative de l’écart CPU avec CronoX et l’équivalence sonore de tous les presets restent non démontrées.
